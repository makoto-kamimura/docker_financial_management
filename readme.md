# カケイカイケイ

> **家計簿から、決算書まで。ひとつの帳簿で。**

家庭の家計管理から、個人事業主の青色申告、法人の決算までを、**同じデータ・同じ画面**で扱う会計アプリ。銀行口座とカードの実際のお金の流れを中心に、予算と実績を比べ、将来の残高を先回りして確かめられる。Web とモバイル（iOS / Android）から使える。

呼称の「カケイカイケイ」は、家計の「カケイ」と会計の「カイケイ」を掛け合わせたもの（旧称：決算管理システム）。リポジトリ名・パッケージ名・Docker のサービス名などの識別子は `financial-management` のままにしている。

## コンセプト

家計簿アプリと会計ソフトは、別々の道具として作られている。そのため、副業を始めたり法人を作ったりすると、家計簿のデータを会計ソフトに入れ直すことになり、銀行口座やカードの明細も、それぞれのアプリに取り込み直すことになる。

カケイカイケイは、**一家庭を一法人に見立てる**ことで、この入れ直しをなくす。

| 考え方 | 内容 |
|---|---|
| 家計も会計も、同じ帳簿で | 家計の「収入・固定費・貯蓄」を、会計の「売上・販管費・利益」と同じ仕組みで記録する。家計 → 個人 → 法人と、使い方が変わってもデータを作り直さない |
| 見る人に合わせて、言葉を変える | 表示モード（家計 / 個人 / 法人）を切り替えると、科目名・用語・メニューがそのモードのものになる。データはそのまま |
| お金の流れは、口座とカードから | 現金・銀行・カードの明細を取り込み、科目を付けた明細がそのまま実績になる。口座間の振替やチャージは、収支から除いて二重計上を防ぐ |
| 先の残高を、先に知る | 予算と、毎月の給与・引き落とし・振替（資金移動ルール）から、先の残高の推移が自動で出る |
| 学びながら、使う | 自分の家計データを教材に、複式簿記・決算・申告書の作り方を学べる |

| 項目 | 内容 |
|---|---|

# 第1部 概要説明

サービスの目的・機能・画面の仕様をまとめる。技術的な内容は[第2部](#第2部-技術説明)に分ける。

## 特徴

| 特徴 | 内容 |
|---|---|
| 3つの表示モード | 家計 / 個人 / 法人 を切り替えると、メニュー・科目名・KPIの呼び方（貯蓄額 ⇔ 営業利益 など）が変わる。データは共通 |
| 予算と実績 | 科目×月の表で予算と実績を管理する。収入に対する配分の目安（適正額）を示し、借入金の返済額は予算に自動で反映する。月ごとに科目別の予実を比べ、差額の扱いを選んで翌月の予算を確定する |
| 銀行管理 | 口座を登録し、残高の推移を見る。明細の CSV の取り込みと、科目を付けるのは実績管理で行う。口座間の振替は、収支から除いて残高だけに反映する |
| 残高の推移 | 予算と資金移動ルールから、口座の先の残高を見込む |
| カード・電子マネー | クレジット・デビット・プリペイドカード・電子マネーの明細を取り込み、チャージや固定決済（サブスクリプションなど）を管理する |
| 資産と借入金 | 口座・実物資産・借入金から総資産（純資産）を出す。変動金利の見直しや残価のある借入にも対応した返済スケジュールを作る |
| 複式簿記の帳簿 | 仕訳帳（承認のワークフローつき）、仕訳テンプレート、総勘定元帳、試算表、売掛金・買掛金、インボイス、棚卸、固定資産と減価償却、事業利用按分 |
| 決算と申告 | 損益計算書・貸借対照表・株主資本等変動計算書・財務分析。青色申告決算書・法人決算書類の印刷、e-Tax 向け XML の出力 |
| 法人管理 | 法人・事業者情報、会計年度、役員・株主総会・配当・決算公告 |
| 勘定科目変換 | 家計の科目を法人の科目へ対応付ける候補を自動で出し、確認して確定する |
| 学習ガイド | 自分のデータを教材に、複式簿記・決算書の読み方・申告書の選び方を学べる |
| 安全性 | 多要素認証（TOTP）、4段階のロール、テナント単位のデータ分離、監査ログ |

## 1. 概要

### 1.1 ポジショニング

家計簿アプリと、個人事業主・中小法人向けの会計ソフトの中間に位置付ける。

| 取り込み元 | 取り込む要素 | 本サービスでの形 |
|---|---|---|
| 家計簿アプリ | 口座・カードの明細の取り込み、予算と実績、資産の推移 | **予算・実績・銀行・カード・資産**（[第8〜12章](#8-予算)） |
| 会計ソフト | 複式簿記、帳簿、決算書、申告書類 | **会計帳簿・決算と申告**（[第13〜14章](#13-会計帳簿)） |
| 独自 | 家計と会計を同じデータで扱う表示モード、残高の見通し、学習ガイド | **表示モード・勘定科目変換・学習ガイド**（[3.3節](#33-表示モード)・[第16章](#16-勘定科目変換学習ガイド外部連携)） |

### 1.2 原則

**データは1つ、見え方は3つ。** 家計・個人・法人のどのモードで入力しても、同じ科目・同じ実績として保存する。モードは見え方（メニュー・科目名・用語）だけを変える。

### 1.3 想定ユースケース

| ユースケース | 使うモード | 主な機能 |
|---|---|---|
| 共働き世帯の家計管理 | 家計 | 予算配分、銀行・カードの明細、残高の推移、住宅ローン |
| 副業・フリーランスの確定申告 | 個人 | 仕訳帳、事業利用按分、減価償却、青色申告決算書 |
| 小さな法人の経理 | 法人 | インボイス、売掛金・買掛金、法人決算書類、ガバナンス |
| 税理士による確認 | 個人・法人 | accountant ロールでの閲覧・仕訳の承認・申告書類の出力（accountant を付ける画面はまだない。[3.1節](#31-ロール)） |
| 家計から法人成り | 家計 → 法人 | 勘定科目変換、学習ガイド |

## 2. 用語

| 用語 | 意味 |
|---|---|
| テナント | データを分ける単位。1つの家庭・個人事業主・法人を表す（種別は個人事業主 / 法人）。1つのテナントに複数のユーザーが所属でき、ユーザーは所属するテナントのデータだけを扱える |
| ロール | ユーザーの権限。admin > editor > accountant > viewer の4段階（[3.1節](#31-ロール)） |
| 表示モード | 家計 / 個人 / 法人。ブラウザ（モバイルはアプリの起動中）ごとの見え方の設定で、データは分けない（[3.3節](#33-表示モード)） |
| 勘定科目 | 収入・支出・資産・負債などの分類。家計の科目名を基本とし、個人・法人モードでの表示名を別に持てる。家計の科目のコードは `H-` で始まる |
| 予算配分・適正額 | 収入に対する各費目の割合の目安（固定費・生活費・その他）。科目は名前のキーワードと区分で自動でどれかの目安に入る。「適正 ¥…」は、その月の収入の実績×目安の割合（幅の中央）を科目に按分したもの（家賃に連携した住宅ローンなどの返済は、その目安の一部として数える）で、予算そのものは変えない。収入の実績が無い月は出さない |
| 自動反映 | 借入金の月々の返済額などを、予算の表示に上乗せすること。予算のデータは変えない |
| 予算の確定・期ズレ | 確定は、月の予算を予実対比の基準として固定すること。確定した月の予算は変えられない。期ズレは、支払いや入金の時期がずれただけの差で、翌月の予算に移す |
| 実績・明細 | 実績は科目×月の金額。現金・銀行・カードの明細は実績と同じ表（`financial_records`）の 1 行で、科目が付いた明細がそのまま実績になる（写しの行は作らない）。科目×月へ直接入れる方法はない |
| 資金移動ルール | 毎月決まった日に発生するお金の動き（給与・収入 / 支出 / 銀行振込 / 銀行引き落とし / カード引き落とし）。出金元・入金先のどちらかは「外部」にできる。残高の推移の見込みに使う。明細の「毎月の入出金」から登録する |
| 振替 | 自分の口座どうしのお金の移動。2つの明細を組にして、収支から除き、残高だけに反映する |
| 引き落とし | 口座から決まった日に引き落とされるもの。銀行引き落としと、カードの利用分をまとめて引き落とすカード引き落としがある |
| カード払いの固定決済 | サブスクリプションなど、カードで決まった日に支払うもの。お金はカード引き落としで口座から出るので、銀行の残高の見込みには含めない（二重計上を防ぐため） |
| チャージ | デビットカード・プリペイドカード・電子マネーへの入金。お金の置き場所が変わるだけなので、収支から除く。クレジットカードはチャージ先にできない |
| 差額（残高調整） | 口座の残高 ＝ 取り込んだ明細の合計 ＋ 差額。明細を取り込み始める前の残高（期首残高）や、取り込めていない明細の分を差額で合わせる |
| 実物資産 | 土地・建物・車・金・貴金属・現金・預金・投資（株式・投資信託）など。借入金をひも付けられる |
| 総資産サマリ | 口座 ＋ 実物資産 − 借入金 で出す純資産 |
| 事業利用按分 | 経費の科目ごとの事業で使う割合（家事按分）。明細を事業利用にしたときの按分の初期値で、按分は明細ごとに持つ。個人モードだけで使う |
| 決算確定 | 会計年度を締めること。取り消して開き直せる |

## 3. ユーザー種別と権限

### 3.1 ロール

| ロール | 段階 | できること |
|---|---|---|
| viewer | 1 | ユーザー管理・監査ログ・税理士ポータル以外の画面の閲覧 |
| accountant | 2 | viewer ＋ 仕訳の承認申請・承認・差戻し、e-Tax XML の出力、税理士ポータル |
| editor | 3 | accountant ＋ データの登録・編集・削除 |
| admin | 4 | editor ＋ ユーザー管理・監査ログ・テナントの作成と削除・予算と実績の確定の解除・会計年度の削除 |

- 各 API は必要な最低のロールを持ち、それより低いロールのユーザーには 403 を返す（[22章](#22-api)）。
- メニューはロールでは出し分けない。権限の無い画面を開くと、データの取得が 403 になる。
- accountant は権限の判定だけがあり、ユーザー管理の画面と API で選べるロールは admin / editor / viewer の 3 つ。今は accountant のユーザーを作れない。

### 3.2 テナント

- すべての財務データはテナントに属し、ユーザーは自分のテナントのデータだけを読み書きできる。
- ユーザー管理（`/admin/users`）も、自分のテナントのユーザーだけが対象になる。
- テナントの種別は個人事業主 / 法人。屋号・法人名、法人番号、資本金、設立日、会計期間（開始月・決算月）を持つ。
- テナントを作ると、家計の既定の勘定科目（83科目。モード別の表示名つき）と予算配分の目安が自動で登録される。

### 3.3 表示モード

表示モードは、ブラウザ（モバイルはアプリの起動中）ごとの設定で、データは分けない。切り替えると次が変わる。

| 変わるもの | 家計 | 個人 | 法人 |
|---|---|---|---|
| システム名 | 家計管理システム | 個人会計システム | 法人会計システム |
| 損益の用語 | 収入 / 変動費 / 収支差額 / 固定費 / 手残り | 売上 / 仕入・変動費 / 粗利 / 経費 / 事業利益 | 売上高 / 売上原価 / 売上総利益 / 販管費 / 営業利益 |
| KPI の呼び方 | 貯蓄額 | 事業利益 | 営業利益 |
| 科目名 | 家計の科目名 | 個人事業主の表示名 | 法人の表示名 |

メニューはモードごとに出し分ける（○＝表示）。

| グループ | 項目 | 家計 | 個人 | 法人 |
|---|---|:-:|:-:|:-:|
| 基本 | ダッシュボード・予算管理・実績管理 | ○ | ○ | ○ |
| 会計帳簿 | 仕訳帳・仕訳テンプレート・総勘定元帳・売掛金管理・買掛金管理・インボイス発行 | | ○ | ○ |
| 資産・経費管理 | 棚卸管理・固定資産 | | ○ | ○ |
| | 事業利用按分 | | ○ | |
| | 資産管理・借入金管理・銀行管理・カード・電子マネー管理 | ○ | ○ | ○ |
| | 外部サービス連携 | | ○ | ○ |
| 決算・申告 | 決算処理 | | ○ | ○ |
| 法人管理 | 法人・事業者情報・ガバナンス管理 | | | ○ |
| | 会計年度管理 | | ○ | ○ |
| 設定・管理 | 勘定科目変換・学習ガイド・税理士ポータル | | ○ | ○ |

## 4. 基本フロー

### 4.1 はじめて使う

1. admin が `/admin/users` でユーザーを作る（新しい家庭・事業として始めるときは「専用の新規テナントを作成する」を選ぶ）。自分で登録する画面はない。
2. `/login` でログインする（多要素認証を有効にしていれば、続けて確認コードを入れる）。
3. 次の 6 つの手順で進める。モバイルアプリでは、ダッシュボードの「ステップ進捗」に進み具合が出る（6 つとも終えると消える。Web では出さない）。
   1. 収入の予算を入れる（予算管理）
   2. 予算管理の「予算の確定」タブの配分提案で、収入の金額から支出の予算を割り振る（はじめての予算のときに出る。割合は「設定」タブ）
   3. 銀行口座を登録する（銀行管理）
   4. 実物資産を登録する（資産管理）
   5. 借入金を登録する（借入金管理。予算に自動で反映される）
   6. 表示モードを一度切り替える

### 4.2 銀行口座とお金の流れを登録する

1. 銀行管理の「銀行口座」で口座を追加する。実際の残高と合わないときは、口座の「編集」から差額を入れる。
2. 明細の CSV を実績管理の「CSV インポート」（取り込み先は銀行）で取り込み、実績管理の「履歴」（出どころは銀行）で明細ごとに科目を付ける（付けた明細がそのまま実績になる）。チャージや毎月の入出金としても登録できる。CSV の無い入出金は、実績管理の「カレンダー」（出どころは銀行）で日付を選んで手で入れる。
3. 実績管理の履歴（出どころは銀行）で、毎月の資金移動ルール（給与・引き落とし・振込など）を明細の「その他」→「毎月の入出金」から登録する。自分の口座どうしの振替は、同じ日・同じ金額の出金と入金が 1 組だけのとき自動で組になる（取り込みのときと「まとめて自動処理」のとき）。履歴では組の解除だけができる。
4. 銀行管理で、残高の推移を確かめる。

### 4.3 カード・電子マネーを登録する

1. カード・電子マネー管理で、カードや電子マネーを登録する。
2. 明細の CSV を実績管理の「CSV インポート」（取り込み先はカード・電子マネー）で取り込み、実績管理の「履歴」で科目を付ける（付けた明細がそのまま実績になる）。手で入れる利用・返金は、実績管理の「カレンダー」で登録する。
3. チャージの明細は、チャージ先の入金の明細と組にする（同じ日・同じ金額が 1 組だけなら自動で組になる）。
4. サブスクリプションなどは、明細から固定決済として登録する。
5. カードの利用分の引き落とし自体は、実績管理の履歴（出どころは銀行）で、引き落としの明細からカード引き落としとして登録する。

### 4.4 予算を立てて実績と比べる

1. 予算管理で、科目×月の予算を入れる（予算配分の目安や CSV の取り込みを使える）。
2. 実績は、科目を付けた現金・銀行・カードの明細と、仕訳から集まる。
3. ダッシュボードで KPI と年間見込みを確かめる。家計モードで赤字の月は、警告を出して貯蓄額のカードを赤くする。
4. ダッシュボードの KPI の上で KPI の対象月の ①②③ の確定状況を、いちばん下で予算と実績のグラフ（差の大きい科目から）を確かめる。
5. はじめて使う月は、予算管理の「予算の確定」でその月を選び、予算を「そのまま確定」する（①）。
6. 銀行・カード・電子マネーの明細を月末まで取り込むと、その月の実績が「入力済み」になる（明細のある口座・カードが 1 つも無いと確定できない）。実績管理の「実績の確定」で「実績を確定」を押す（②）。月末まで明細が届かない口座・カードは、最終日のあと取引が無ければ「当月末まで変動なし」を押して確定できる。
7. 予算管理の「予実差確認」で、その月の科目ごとの予算と実績の差を確かめる。
8. 予算管理の「予算の確定」で翌月を選び、前月の差額の扱い（何もしない・期ズレとして翌月へ・回し先へ）を選ぶと、翌月の予算案ができる。必要なら案の金額を直す（流用）。「確定」を押すと、案が翌月の予算になり、翌月の予算は確定済みになる（③）。翌月が終わったら 6 から繰り返す。

### 4.5 借入金を管理する

1. 借入金管理で借入を登録する（種類・金利・残価・予算に反映する科目）。
2. 変動金利が見直されたら「金利変更の登録」で新しい金利（通知された返済額があればそれも）を入れる。見直し前後の比較が出る。
3. 返済を登録する。月々の返済額は予算に「自動反映」として上乗せされる。

### 4.6 帳簿をつけて決算・申告する（個人・法人モード）

1. 仕訳帳で取引を記録する。必要なら承認のワークフロー（承認申請 → 承認 / 差戻し）を通す。
2. 売掛金・買掛金・インボイスを管理する。
3. 期末に、棚卸・固定資産の減価償却・事業利用按分（個人のみ）を済ませる。
4. 決算処理で決算書を確かめ、決算を確定する。
5. 青色申告決算書（または収支内訳書）・法人決算書類を印刷し、必要なら e-Tax 向けの XML を出力する。

### 4.7 家計から法人会計へ切り替える

1. 表示モードを家計から法人へ切り替えると、勘定科目変換を開くかを確認する。
2. 家計の科目ごとに、法人の科目の候補が自動で出る。確かめて確定する。手で直した対応は、次からの候補に使われる。
3. 学習ガイドで、家計と法人会計の対応や決算の流れを学べる。

**金額の向きの表し方**（言葉は `src/lib/shared/amount-direction.ts`、Web は `src/components/DirectedAmount.tsx`）。入ってくる向き（実質プラス）は緑、出ていく向き（実質マイナス）は赤にそろえ、金額の前にラベルを付ける。カレンダーのマスは 1 文字のラベル。

| 場面 | 入ってくる向き（緑） | 出ていく向き（赤） |
|---|---|---|
| 銀行の明細・未割り当ての明細 | 入金（入） | 出金（出） |
| 現金・予算のカレンダー | 収入（収） | 支出（支） |
| カード | 返金（返） | 利用（利） |

- 予実の差: 「余り」「超過」「上振れ」「不足」「予算どおり」と金額（色は有利なら緑、不利なら赤）。
- 増減（翌月の予算案・期ズレ・回し先）: 「5,000円増」「5,000円減」。
- 差引・利益が負のとき: 「赤字 1,234円」（銀行カレンダーの差引は「出金超過」、事業所得は「損失」、純資産は「債務超過」）。
- 科目の実績が負のとき（返金などが上回った月）: 費用は「戻り」、収入は「減額」。
- 借入の比較: 「12,000円増える／減る」「0.25pt 上昇／低下」。資産の年率の目安: 「年 1.5% 上昇／下落」。
- 残高・グラフの軸・会計の帳票（決算の印刷・元帳）は、負の数に「−」や「△」を使う。CSV の取り込みは、明細そのままの符号（入金は正、支出は負）で受け取る。

大きい画面は、タブやモーダルごとの部品を `src/components/<画面>/` に分けて置く（`page.tsx` はタブの切り替えと、開いているモーダルの状態だけを持つ）。モバイルの `src/components/bank/`・`card/` と同じ置き方。

## 6. 認証とアカウント

### 6.1 ログイン

- メールアドレスとパスワードでログインする。ログインのあとは常にダッシュボードへ進む。
- パスワードを5回続けて間違えると、そのアカウントは15分ロックされる。これとは別に、同じ IP からのログインは 5 分に 10 回までにする。
- パスワードは 8 文字以上。本人は変えられず、admin がユーザー管理で再設定する。admin がパスワードかロールを変えると、そのユーザーのセッションはすべて切れる。
- セッションは、最後の操作から24時間、またはログインから7日で切れる（環境変数 `SESSION_IDLE_HOURS`・`SESSION_ABSOLUTE_DAYS` で変えられる）。切れたら、ログイン画面に理由を表示して戻す。

### 6.2 多要素認証

- 設定のセキュリティで、認証アプリ（TOTP）を登録して有効にする。
- 有効にすると、ログインの2段階目で6桁の確認コードを求める。2段階目は 5 分以内に入れる。5 回間違えると 15 分ロックされる。
- 確認コードを入れられないときのために、使い捨てのリカバリーコード（8 個）を発行できる。再発行と多要素認証の無効化には確認コードが要り、無効化するとリカバリーコードも消える。

### 6.3 ユーザーとテナントの作成

- ユーザーは admin が `/admin/users` で作る。既定では作った人と同じテナントに所属する。
- 「専用の新規テナントを作成する」を選ぶと、新しいテナント（名前はユーザーの表示名。家計の既定の科目と予算配分の目安つき）を作ってそこに所属させる。
- 手順は [runbooks/users-and-tenants.md](docs/runbooks/users-and-tenants.md) にまとめている。

### 6.4 監査ログ

ログインと、予算・実績と明細・銀行口座・カード・資金移動・科目・予算配分・部門・ユーザー・多要素認証・取り込み・証憑の削除とダウンロードの操作を記録する。変更前後の内容は、渡している操作だけ残す。パスワードなどの秘密の値は伏せて記録する。仕訳・借入金・実物資産・インボイス・売掛金と買掛金・固定資産・棚卸・決算・法人の情報など、帳簿と法人の操作は今は記録しない（各 API が `audit()` を呼んだときだけ記録する）。

admin が `/admin/audit` で見られる（自分のテナントの記録だけ。操作したユーザーは今の表示名で出し、削除されたユーザーは「削除されたユーザー（#id）」と出す）。表示名の変更は、変更前と変更後の名前を残す（本人の変更は `update_profile`）。

## 7. ダッシュボードと予測

### 7.1 ステップ進捗

[4.1節](#41-はじめて使う)の6つの手順の進み具合を、モバイルアプリのダッシュボードに表示する。すべて終えると消える。Web のダッシュボードからは、いったん外した（データは `GET /api/onboarding/steps`、判定は `src/lib/shared/step-checklist.ts` で、どちらも残している）。

### 7.2 KPI

対象月の収入（売上）・支出または売上総利益・利益・累計（YTD）を、表示モードの用語で表示する（家計なら収入・支出・貯蓄額）。対象月の既定は、今月以前でデータのある最新の月。

- **期の区切り**：累計と年間見込みは、テナントの会計期間（開始月 `tenants.startMonth`〜決算月 `tenants.closingMonth`、既定 1〜12 月）の 1 年で集計する。12 月決算なら「当年累計」（1〜12 月）、それ以外は「当期累計」とし、期間を添える。会計期間は設定の基本設定（全モード）か法人ページで変える。開始月は決算月の翌月でなければ保存できない（API が 400 を返し、DB の CHECK 制約でも拒否する）。予算表・決算書などの年度は暦年のまま。
- **年間見込み**：期首から「実績として扱う最後の月」までの累計に、次の 2 つを足す。計算は `src/lib/accounting/kpi.ts` `computeAnnualOutlook`。
  - 実績として扱う最後の月：対象月より前に実績を確定した月があれば、その最後の月。明細が途中までしか無い未確定の月で見込みがぶれないようにするため。実績の確定を使っていないときと、確定済みの月を見ているときは対象月。
  - 期首からその月までで入力の無い月：その期で入力のある月の平均で埋める（按分）。入力が 1 か月だけでも、1 年分の目安が出る。
  - その月より後の月：入力があっても、移動平均（直近 3 か月）で予測する。
- 累計カードには収入の年間見込みと達成率（累計 ÷ 年間見込み）を、利益カードには利益（家計は貯蓄額）の年間見込みを出す。どちらも「未入力Nか月は平均・M月以降は予測」の内訳を添える。
- 各カードには、予算と達成率（支出は消化率）を添える。個人・法人の売上総利益（粗利）のカードには粗利率を出す。営業利益率・前月比・前年同月比は出さない。

ページの見出しのすぐ下（KPI より上）に、次を置く。

- **予算と実績の確定の状況**：KPI の対象月の ① 予算 → ② 実績 → ③ 翌月の予算 の確定状況を 1 行で出す。各段は予算管理・実績管理の確定タブ（① はその月、③ は翌月の予算の確定）へのリンク。確定の操作はここでは行わない（[8.5節](#85-予算と実績の確定)）。データは `GET /api/cycle-status`。

KPI の下に、次の順で置く。

- **総資産サマリ**：KPI の対象月の時点（月末、今月なら今日）の総資産・総負債・純資産と内訳（[12.1節](#121-総資産サマリ)）。データは `GET /api/assets/summary?year=&month=`。
- **総借入サマリ**：同じ時点の借入残高・月々の返済額・借入総額と、借入ごとの残高・月々・金利・完済予定（資産のローンも含む）。残高は借入金管理と同じ計算（[12.3節](#123-借入金)）。データは `GET /api/loans/summary?year=&month=`。
- **口座残高サマリ**：同じ時点の総残高・口座数・最終更新（明細を最後に登録した日時）と、口座ごとの残高。残高は銀行管理と同じ定義（明細の合計 ＋ 差額。[10.1節](#101-口座と残高)）で、明細はその月の終わりまでを数える。データは `GET /api/bank-accounts/summary?year=&month=`。
- **予算と実績のグラフ**：KPI の対象月について、収入・支出の合計と科目別に、予算（灰色の帯と右端の線）と実績（棒）を横棒で重ねる。実績の色は、有利（支出が予算内・収入が予算以上）なら青、不利なら赤、予算が無いか差が無ければ灰色。色だけに頼らず「余り／超過／上振れ／不足」と差額を文字でも出す。科目は差の大きい順に上位 6 科目を出し、残りは「その他」にまとめる（残りが 1 科目ならそのまま出す）。整形は `src/lib/shared/budget-actual-chart.ts`（モバイルと共有）、データは `GET /api/budgets/variance`。

### 7.3 予測

- 年間見込みの残りの月は、移動平均（直近 3 か月）で予測する（[7.2節](#72-kpi)）。
- API では、予測手法を移動平均・線形回帰・成長率・Holt・Holt-Winters から選べる。どちらの API も、今は画面からは使っていない。
  - `GET /api/reports/monthly-trend`：月ごとの推移と予測（既定は移動平均）。
  - `GET /api/forecasts`：科目ごとの予測と、過去のデータで検証した精度（MAPE・RMSE）、楽観・基準・悲観のシナリオ（既定は線形回帰）。`POST` で予測をスナップショットとして保存できる（`forecasts`）。

### 7.4 グラフ

- ダッシュボードのグラフは、予算と実績のグラフだけを置く（カテゴリ構成比・月別カテゴリ内訳は置かない）。
- 家計モードで赤字の月は、KPI のカードの中（対象月の選択の下）に警告を出し、貯蓄額のカードを赤くする（月ごとの収支の表は置かない）。

## 8. 予算

### 8.1 明細一覧とカレンダー

- 科目×月の表で予算を入力・編集する。
- カレンダーでは、実績管理のカレンダー（手動）と同じ形で、日付を選んで予算を登録する（支出 / 収入・摘要・科目・金額）。登録した 1 件は `budget_items` に残り、同じ科目・月の予算（`budgets.amount`）に足す。削除すると引く。予算を確定した月は登録・削除できない（409）。`POST /api/budget-items`・`DELETE /api/budget-items/[id]`・`GET /api/budget-items?year=&month=`。
- カレンダーの登録があるセル・出どころが 2 つ以上あるセルには「N件」を出し、押すと内訳を開く。内訳は、カレンダーの登録（1 件ずつ）・一覧・CSV・予算配分などで入れた額（予算からカレンダーの合計を引いた残り）・借入の返済と資産の借入の自動加算に分ける（`src/lib/shared/budget-cell-detail.ts`、モバイルと共有）。カレンダーの登録があるセルは、合計をその場では書き換えない。
- 一覧でセルの予算を削除すると、その科目・月のカレンダーの登録も消える。

### 8.2 予算配分

収入に対する費目ごとの割合の目安（予算配分ルール）から、支出の予算を提案する。既定の目安は次のとおり（予算管理の「設定」タブで変えられる）。

| グループ | 費目（割合の目安） |
|---|---|
| 固定費 | 家賃・住宅ローン（20〜30%）、水道・光熱費（4〜6%）、通信費（3〜5%）、保険料（4〜6%）、その他の固定費（0〜4%、受け皿） |
| 生活費 | 食費（12〜18%）、車関連（0〜10%）、日用品・衣服（3〜5%）、教育費（0〜10%）、その他の生活費（0〜4%、受け皿） |
| その他 | 娯楽・交際費・小遣い（6〜10%）、貯蓄・投資（10〜30%） |

推奨額は幅の中央で、上限の無いルールは下限を使う。既定の目安は、中央の合計がちょうど 100% になるように決めている。手取りに対する FP の目安（住居 25%・食費 15%・光熱と通信と保険がそれぞれ 5% 前後・貯蓄 20%）に合わせた。子どもや車が無い世帯のために、教育費と車関連は下限を 0% にしている。

個人事業の予算（[20.15節](#2015-事業利用と按分)）には、別の配分ルールを持つ。既定の目安は売上に対する割合で、中央の合計はやはり 100%。余りの回し先の既定は「事業主の取り分」に入る科目。

| グループ | 費目（割合の目安） |
|---|---|
| 変動費 | 仕入・材料（20〜40%）、外注費（5〜15%）、広告宣伝費（2〜8%）、旅費交通費（1〜5%）、消耗品費（1〜5%）、その他の原価（0〜4%、受け皿） |
| 固定費 | 地代家賃（5〜15%）、通信費（1〜5%）、水道光熱費（1〜3%）、その他の経費（0〜4%、受け皿） |
| その他 | 接待交際費（0〜4%）、支払手数料（0〜4%）、事業主の取り分（利益、20〜32%） |

**科目の振り分け**：科目はルールに直接結び付けず、その場で振り分ける（保存しないので、追加した科目もすぐ入る）。計算は `src/lib/shared/allocation-assign.ts`。

1. 手で割り当てた科目（`allocation_account_assignments`）は、その割り当てに従う。「配分に入れない」も選べる。
2. 科目名がルールのキーワードを含めば、そのルールに入る（大文字小文字・全角半角は区別しない）。複数のルールに当たったら、科目名の先頭に近い位置で当たったものを採る。同じ位置なら長いキーワードを採る（例: 「娯楽/外食費」は娯楽・交際費、「自動車保険」は保険料）。
3. どれにも当たらなければ、区分の受け皿（`fallbackCategory`）に入る。固定費はその他の固定費、変動費はその他の生活費。
4. 受け皿も無い区分の科目は未分類として画面に出す。

対象は変動費・固定費・貯蓄の区分だけで、1 科目は 1 ルールにだけ入る。社会保険・税は保険料のキーワードに入れていないので、その他の固定費に入る。画面では、ルールごとに入っている科目をチップで出す。チップから、別のルールへ移す・配分から外す・自動に戻すができる。設定の科目名設定にも、科目が入っているルールを出す。

**金額の分け方**：1 ルールに複数の科目があるときは、ルールの金額を前の 3 か月の実績の比率で科目へ按分する（実績が無ければ均等）。

- **借入の返済（自動反映）**：返済の連携先の科目がどれかのルールに入っていれば、返済はそのルールの目安の一部として数え、基準額からは引かない。たとえば家賃に連携した住宅ローンは、家賃・住宅ローンの枠（25%）を先に埋め、残りだけを管理費などへ回す（住居費を二重に数えない）。どのルールにも入っていない科目に連携した返済だけは、基準額から引く。
- 予算の表の「適正 ¥…」：その月の収入の実績（どのルールにも入っていない返済は引く）に、ルールの目安の割合（幅の中央。上限の無いルールは下限）を掛け、科目へ按分した参考値。返済のある科目は返済の額で埋まっているものとし、ルールの残りを他の科目へ按分する（`splitRuleTarget`）。予算の有無に関係なく出し、予算は変えない。収入の実績が無い月は出さない。
- 配分提案は、はじめての予算の確定（前月にも予算の月にも実績が 1 件も無く、予算の月が未確定）のときだけ、「予算の確定」タブに予算の月に固定して出す（`components/AllocationSuggestSection.tsx`。判定は cycle-status の `actuals.recorded`）。「設定」タブには配分ルールだけを置く。基準額は「手入力 / 収入の実績 / 収入の予算」から選べる（`GET /api/budgets/allocation-suggest`）。予算へ反映すると、その月の「予算をそのまま確定」が出る。実績・予算のときは返済を上と同じように扱い、返済のある科目は「入っている予算」として扱う。
- 「予算へ反映」：予算が未設定の科目にだけ入れる。ルールの金額から、同じルールの科目に入っている予算を差し引き、残りを未設定の科目へ按分する。残りが 0 以下なら何もしない。すでに予算が入っている科目は書き換えない（サーバー側でも飛ばす）。

### 8.3 自動反映

借入金の月々の返済額（予算に反映する科目を指定したもの）と、実物資産にひも付けた借入の返済を、予算の表示に上乗せして「自動反映」の印を付ける。予算のデータは変えない。

### 8.4 履歴

- 予算の登録・変更・削除は履歴に残る。予算を消しても、履歴は科目と月とともに残る。

### 8.5 予算と実績の確定

月ごとに、予算と実績を確定し、科目ごとに比べて翌月の予算を確定する。会社の予算管理にならい、確定した予算と実績は比べる基準として固定し、予算の余りは原則として繰り越さない。

月ごとに次の順に進める。順番は API が強制し、守られていない操作は 409 で断る。

| 段 | 操作 | 条件 |
|---|---|---|
| ① | その月の予算を確定 | 前月の予算が確定済みなら、前月の実績も確定済みであること（前月の予算が未確定ならサイクルの初回とみなし、そのまま確定できる）。期の最初の月にも例外は無い |
| ② | その月の実績を確定 | その月の予算が確定済みで、実績が「入力済み」であり、未割り当ての明細が無いこと。明細のある銀行口座・カードが 1 つも無い月は確定できない |
| ③ | 翌月の予算を確定 | その月の実績が確定済みであること（＝翌月にとっての ①） |

解除は逆の順でしか行えない（翌月の予算 → 実績 → 予算）。

予算は家庭と個人事業で別々に持ち、①③ の予算の確定も別々に行う。② の実績の確定は共通で、その月の予算がどちらかで確定していればよい（[20.15節](#2015-事業利用と按分)）。

画面は 3 つに分かれる（モバイルも同じ）。年は左のメニュー（モバイルは画面上部）の対象年度で選び、画面では月だけをボタンで選ぶ。既定の月は、最後に実績を確定した月 L から決める（予実差確認は L、予算の確定と実績の確定は L の翌月。一度も確定していなければ前月）。最後に確定した月は `GET /api/cycle-status/latest` で返し、決め方は `src/lib/shared/cycle-month.ts`（モバイルと共有）。状況はダッシュボードにも出る（[7.2節](#72-kpi)）。

- **予算管理の「予実差確認」**：選んだ月の予実対比を見る（下の 3）。
- **予算管理の「予算の確定」**：選んだ「予算の月」の予算を確定する。前月の差額の扱いを選んで予算案を作る（その月から見た ③）か、いま入っている予算のまま確定する（①）（下の 4〜6）。
- **実績管理の「実績の確定」**：②。明細の最終日と実績の確定（下の 1〜2）。

①②③ の状況は `src/lib/budget/cycle-status.ts` で出し、`GET /api/cycle-status` と `GET /api/budgets/variance` が同じ形で返す。

1. **実績の入力状況**：銀行口座（`bank_accounts`）とカード・電子マネー（`linked_accounts`）ごとに、取り込んだ明細の最終日（取引日の最大値）を出す。明細のあるソースの最終日のうち一番古い日が月末日以降なら「入力済み」とする（最終日の当日も入力済みに含める）。明細が 1 件も無いソースは判定から外す（使っていないカードで止まらないようにするため）。その月の未割り当て（科目が付いていない）の明細の件数も出す。計算は `src/lib/ledger/actuals-coverage.ts`。
   - **当月末まで変動なし**：月末まで届いていないソースは、行ごとのボタンで「当月末まで変動なし」の印を付けられる（最終日のあと月末まで取引が無いと申告する）。届いていないソースすべてに印を付ければ、入力済みと同じく確定できる。
2. **未割り当ての明細**：その月の科目が付いていない明細（現金・銀行・カード。振替・チャージの組は除く）を確定のタブに並べ、行ごとに科目と事業利用・按分を選べる（`GET /api/ledger/unassigned`。選ぶと学習し、同じ摘要の未割り当ての明細にも付く。「割り当て済みも表示」で `?includeAssigned=1` になり、科目を付けた明細も見直せる）。ある月のある科目の明細をまとめて事業利用にすることもできる（`PATCH /api/ledger/business`。[20.15節](#2015-事業利用と按分)）。残っている間は確定できない（409）。「まとめて自動処理」（`POST /api/ledger/auto-process`。`src/lib/ledger/ledger-auto-process.ts`）は、全期間の未割り当ての明細に学習ルール（[9.4節](#94-学習ルール)）で科目を付け、自動相殺（[20.4節](#204-振替とチャージ)）をかける。「科目を付け直す」（`?reset=1`）は、科目の付いた明細も対象にし、ルールに当たればその科目に付け直し、当たらなければ未割り当てに戻す（手で選んだ科目も外れる）。どちらも振替・チャージの組と確定済みの月の明細は変えない。
3. **実績の確定**：「入力済み」になり（または届いていないソースすべてに変動なしの印を付け）、未割り当ての明細が無くなったら、ユーザーがボタンで確定する（自動では確定しない）。確定時点の明細の状況（ソースごとの最終日と変動なしの印）を `actuals_confirmations.coverage` に記録し、確定済みの月はその記録を表示する。確定した月の実績（`financial_records`）は、明細の登録・削除・科目の変更・振替やチャージの紐付け・仕訳（P/L 科目を含むもの）・売掛金／買掛金の登録・減価償却・棚卸の確定を受け付けない（409）。CSV と自動取得の取り込みでは、確定した月の行を飛ばす（件数を返す）。解除は admin だけができ、実績の値は変えない。確定と解除は監査ログに残す（`actuals_confirm` / `actuals_unconfirm`）。
4. **予実対比**（予実差確認）：選んだ月の収入・費用（`REVENUE` / `COGS` / `EXPENSE`）の科目ごとに、予算（自動反映を含む）・実績・差（実績−予算）を出す。費用は実績が予算より少なければ「余り」、多ければ「超過」とする。
5. **差額の扱い**（予算の確定）：予算の月の前月の差について、科目ごとに次から選ぶ。計算は `src/lib/shared/budget-cycle.ts`。

   | 扱い | 翌月の予算案 | 既定 |
   |---|---|---|
   | 何もしない | 基準額のまま | 個人・法人モードのすべて。家計の超過と収入 |
   | 期ズレとして翌月へ | 基準額 ＋（予算 − 実績）。使わなかった分は足し、先に使った分は引く。0 円未満は 0 円にする | — |
   | 回し先へ | 余りを回し先の科目の予算に足す（費用の科目で余ったときだけ選べる） | 家計の余り（回し先があるとき） |

   - 予算の月の基準額は、その月に予算が入っていればその額、無ければ前月の予算（引き継ぎ）。
   - 回し先の既定は、予算配分ルール「貯蓄・投資」にひも付けた科目。画面で変えられる。
   - 科目の間で予算を移す（流用する）ときは、案の金額を直接書き換える。
6. **予算の確定**：「確定」で案を予算の月の予算に書き込み（変更履歴も残す）、その月を確定済みにする。前月の実績が確定済みであることが条件。予算をそのまま確定することもできる。前月にも予算の月にも実績が無いはじめての予算は、案の代わりに出る配分提案で入れてから、そのまま確定する。
7. **予算が確定済みの月**：予算の登録・変更・削除・カレンダーの登録・予算配分の反映を受け付けない（409）。明細一覧の月の見出しに鍵の印を付ける。確定の解除は admin だけができ、予算の値は変えずに確定の印だけを外す。確定と解除は監査ログに残す。

## 9. 実績

### 9.1 明細一覧とカレンダー

- 実績と明細は 1 つの表（`financial_records`）に載る。現金・銀行・カードの明細は `kind`（CASH / BANK / CARD）を持つ行で、科目（`accountId`）が付いた行がそのまま実績になる。科目が付いていない明細は「未割り当て」で、実績には入らない（`amount` は 0）。
- 科目×月の表は見るだけにした（科目×月へ直接入れる・変える・消すことはできない。`POST /api/financials`・`PATCH`・`DELETE /api/financials/[id]`・`POST /api/financials/import` は 410 を返す）。値のあるセルは 1 件でも「○件」（モバイルは「○件の内訳」）を出し、押すと内訳を開く。
- カレンダーと履歴は、上で出どころを選ぶ（種別 → 口座の 2 段階）。
  - 現金: 現金での支出・収入の明細。カレンダーで科目を選んで登録し（`POST /api/actuals`。登録した時点で実績になる）、履歴で科目の変更（`PATCH /api/actuals/[id]/categorize`。銀行・カードと同じく学習する）・削除を行う
  - 銀行: 入出金の明細。カレンダーで入金・出金を登録し（科目を選べる。「自動」なら学習ルールで決め、当たらなければ未割り当て）、履歴で科目付け・チャージ・振替の解除・毎月の入出金の登録・削除を行う（[10.2節](#102-明細)）。口座は「すべての銀行」も選べる
  - カード・電子マネー: 利用・返金の明細。カレンダーで登録し（科目は銀行と同じ）、履歴で科目付け・チャージ先・固定決済の登録・削除を行う（[11.2節](#112-明細と科目付け)）
- 銀行管理・カード管理の「明細を見る」から、その口座の履歴を開ける。

### 9.2 実績の出どころ

表のセルを開くと、金額の内訳を出どころごとに表示する。

| 出どころ | 内容 |
|---|---|
| 現金の明細 | [9.1節](#91-明細一覧とカレンダー) |
| 銀行の明細 | [10.2節](#102-明細) |
| カードの明細 | [11.2節](#112-明細と科目付け) |
| 仕訳と連動 | 仕訳帳の仕訳から作られた実績。仕訳を消すと一緒に消える |
| 過去の直接入力 | 科目×月へ直接入れていたころの実績。そのまま残して読む |

### 9.3 CSV インポートと履歴

- **CSV インポート**は、現金・銀行・カード・電子マネーの明細を 1 か所にまとめた。`POST /api/imports?target=cash|bank|card&accountId=`、振り分けは `src/lib/ledger/ledger-import.ts`。
  - 列は 取り込み先・日付・摘要・金額・残高（英語の `account,date,description,amount,balance` も可）。科目の列は無い。
  - 取り込み先の列があれば、行ごとに振り分ける（1 つのファイルで複数の口座・カード・現金をまとめて登録できる）。取り込み先は銀行口座・カード（電子マネー）の名前か「現金」。同じ名前の口座とカードがあると決められないので誤りにする。
  - 取り込み先の列が無ければ、上で選んだ取り込み先（現金 / 銀行 + 口座 / カード + カード）に入れる。取込先の確認を出す。銀行のときは自動取得（同期）も置く。
  - 金額は明細そのまま（入金は正、支出は負。カードの利用も負）。
  - 摘要が学習ルール（[9.4節](#94-学習ルール)）に当たった明細には科目が付き、そのまま実績になる。当たらなかった明細は未割り当てになり、実績の確定のタブで科目を付ける。
  - 取り込んだ日付の明細に自動相殺（[20.4節](#204-振替とチャージ)）をかける。
  - 取り込み先が「実績」の行と `target=actual` は受け付けない（実績は明細から入る）。
  - カードに取り込むときは、そのカードのチャージのルール（`card_transfer_rules`、[11.3節](#113-チャージ)）に当たった行をチャージにして、科目を付けない。
  - ファイルは 5MB・10,000 行まで。取り込みは 1 ユーザー 10 分に 10 回まで。
  - 誤りのある行が 1 つでもあれば、どの行も取り込まない（行番号つきで返す）。同じ明細（口座・日付・金額・摘要が同じもの。同じ日に同じ店で同じ金額を 2 回使った 2 件目も重複になる。現金は口座が無いので、同じ内容の現金の明細があれば重複とする）は重複として、実績を確定済みの月の行は確定済みとして飛ばし、それぞれの件数と、自動相殺で組にした数を返す。
- **履歴は共通の表**（`src/components/LedgerTable.tsx`。モバイルは `components/LedgerRow.tsx`）にした。列は 日付 / 口座 / 摘要 / 金額 / 科目 / 状態 / 操作 で、件数・絞り込み・ページ送り（30 件ずつ）の位置も同じ。
  - 現金: 現金の明細（直近 200 件）。科目を選び直せ、削除できる。
  - 銀行・カード: 状態に取得元・実績 / 未割り当て・チャージ・毎月の入出金（固定決済）のバッジを出す。チャージ先・毎月の入出金（固定決済）・削除は「その他」にまとめる。「全件 / 未割り当て / 実績」で絞り込める。
  - 科目を付けると学習し、同じ摘要で未割り当ての同じ種別の明細にも同じ科目を付ける（[9.4節](#94-学習ルール)）。

### 9.4 学習ルール

明細の摘要から科目を決めるルール（`txn_category_rules`）。テナントごとに持ち、現金・銀行・カード・電子マネーで共通に使う。画面では、実績管理の CSV インポート・履歴・設定のタブと、実績の確定タブの未割り当ての明細に、開閉式の「学習ルールのしくみ」として出す（文言は `src/lib/shared/help-texts.ts` の `LEARNING_RULE_TERMS`）。

**事業利用**：ルールは事業利用も持てる（`businessUse` が true なら按分 `businessRatio` も、false なら事業利用なし、null ならルールでは決めない）。明細に科目と一緒に事業利用を付けたときに覚え、科目だけを変えたときは覚えた事業利用を残す。当たった明細には、科目と一緒に事業利用も付ける（CSV の取り込み・自動取得・手入力・まとめて自動処理）。

**一覧と変更**：実績管理の「設定」タブ（Web は `src/components/entry/LearningRulesPanel.tsx`、モバイルは `LearningRulesSection`）で、ルールを一覧し、キーワードと科目を直したり、追加・削除したりできる。予算管理の「設定」（予算配分ルール）と同じ形で、「変更を保存」でまとめて保存する（`GET` / `PUT /api/ledger/category-rules`）。キーワードは覚えるときと同じく正規化して保存し、空や重複は 400。科目は収入・支出の科目だけ。画面で足したルールは、覚えたルールと同じ優先度（100）。ルールを変えても、すでに付いている明細の科目は変わらない（付け直すのは実績の確定タブの「科目を付け直す」）。

**覚えるとき**

- 明細に科目を付けたときに覚える（`PATCH /api/actuals/[id]/categorize`・`/api/bank-transactions/[id]/categorize`・`/api/card-transactions/[id]/categorize` に `learn: true`。処理は `src/lib/ledger/ledger-categorize.ts`）。画面は、履歴（現金・銀行・カード）と実績の確定タブの未割り当ての明細で、科目を選ぶと送る。モバイルも同じ。
- 未割り当てに戻したとき（`categoryAccountId: null`）は覚えず、ルールも消さない。
- カレンダーで登録するときに選んだ科目と、「まとめて自動処理」「科目を付け直す」では覚えない。

**覚える内容**

- 摘要全体を正規化したものを、そのままキーワードにする（前後の空白を除き、続く空白を 1 つにまとめ、大文字にする。全角・半角はそろえない。`src/lib/ledger/banktxn-import.ts` の `normalizeKeyword`）。
- 手で覚えたルールの優先度は 100。同じキーワード（`tenantId` + `keyword` で一意）があれば、科目を上書きする。

**当てかた**（`classifyByRules`）

- 明細の摘要を同じく正規化し、キーワードを含めば当たり（部分一致）。「AMAZON」を覚えると「AMAZON MARKETPLACE」にも当たるが、「AMAZON MARKETPLACE」を覚えても「AMAZON」には当たらない。
- 優先度の高い順 → キーワードの長い順に見て、最初に当たったルールの科目を使う。今は覚えたルールがすべて優先度 100 なので、長いキーワードが勝つ。
- どれにも当たらなければ未割り当て（実績に入らない）。

**使う場面**（`src/lib/ledger/ledger-entries.ts` の `loadRuleClassifier`）

| 場面 | 対象 |
|---|---|
| CSV の取り込み・自動取得 | 取り込んだ明細（[9.3節](#93-csv-インポートと履歴)） |
| カレンダーの登録 | 科目を「自動」のまま登録した銀行・カードの明細（`entryCategory`） |
| まとめて自動処理 | 全期間の未割り当ての明細（[8.5節](#85-予算と実績の確定) の 2） |
| 科目を付け直す | 全期間の、科目の付いた明細も含めた明細。当たらなければ未割り当てに戻す |

**同じ摘要の明細**

- 科目を付けたときは、同じ摘要（正規化して一致）で未割り当ての明細にも、その場で同じ科目を付ける（件数を `updatedSiblingCount` で返す）。その場で付けるのは同じ種別（現金どうし・銀行どうし・カードどうし）だけで、ほかの種別の明細には、次に取り込んだときや「まとめて自動処理」で付く。
- 振替・チャージの組の明細と、実績を確定済みの月の明細は、どの場面でも変えない。

**直すとき**

- ルールを一覧で見る・消す API と画面は無い。間違って覚えたときは、同じ摘要の明細に正しい科目を付け直すと上書きされる。すでに科目の付いたほかの明細は変わらないので、「科目を付け直す」で付け直す。

## 10. 銀行管理

### 10.1 口座と残高

- 口座には、名前・銀行名・支店名・種別（普通 / 当座 / 定期）・口座番号・下 4 桁・紐付く科目（資産か負債）・メモを登録する。編集では支店名と種別は変えられない。役割（給与 / 引き落とし / 貯蓄 / その他）の列は API だけにあり、画面からは設定しない。
- 残高は「取り込んだ明細の合計 ＋ 差額」で出す。明細を取り込む前の残高などは、差額で合わせる。
- 銀行管理は、残高の推移と銀行口座だけを、常にすべての口座で出す（口座を選ぶ切り替えは削除した）。
- 口座の登録・編集・削除は、いちばん下の「銀行口座」で行う。口座ごとの残高のまとめはダッシュボードの口座残高サマリに出す（[7.2節](#72-kpi)）。
- 明細がある口座で差額をまだ確かめていなければ、「実際の残高と違う場合は「編集」から差額を入力」と案内する。編集で差額を保存すると（0 円でも）確かめ済み（`balanceCheckedAt`）になり、差額 0 円なら「明細合計どおり（差額なし）」と出す。
- この残高を、総資産サマリ・口座残高サマリ・残高の推移のすべてで使う。

### 10.2 明細

- 明細は実績管理の CSV インポート（列は 取り込み先・日付・摘要・金額・残高。[9.3節](#93-csv-インポートと履歴)）で取り込むか、実績管理のカレンダー（出どころは銀行）で日付を選んで手で入れる（入金 / 出金・摘要・金額・科目）。月の入金・出金の合計と、日ごとの増減を出す。すべての銀行のときは、登録する口座を選ぶ。
- 明細は実績管理の履歴（出どころは銀行）に並べる。すべての銀行のときは全口座の明細を日付順にまとめ、口座名を添える。同じ明細を二重に取り込まないように、明細ごとの識別子で重複を除く。
- 自動取得（同期）の仕組みもあるが、今はモックの取得先だけで、実際の銀行にはつながない（[25章](#25-未決事項)）。
- 明細ごとに次を行える。

| 操作 | 内容 |
|---|---|
| 科目を付ける | 取り込み時は摘要のキーワードから、学習したルールで科目を補う。履歴で選んでも付けられる。科目を付けた明細がそのまま実績になる |
| チャージにする | チャージ先（デビット・プリペイド・電子マネー）を選ぶ。収支から除く |
| 振替の解除 | 自動で組になった振替を外し、別々の明細に戻す。以後それぞれ科目を付けられる |
| 毎月の入出金に登録する | 「その他」から、毎月の資金移動ルールとして登録する |
| 削除 | 明細を消す（振替の組なら相手の明細も消える） |

### 10.3 振替と資金移動ルール

- **資金移動ルール**：毎月の決まった日のお金の動きを、種類（給与・収入 / 支出 / 銀行振込 / 銀行引き落とし / カード引き落とし）・日・金額・出金元・入金先で登録する。出金元・入金先は「外部」にできる（給与は外部から入金、支出は外部へ出金）。
- ルールは、実績管理の履歴（出どころは銀行）の明細の「その他」→「毎月の入出金」から登録・書き換え・解除する（`POST /api/transfers`・`PATCH / DELETE /api/transfers/[id]`）。登録済みの明細には「毎月の入出金」のバッジが付く。残高の推移の見込みと、カード・電子マネー管理の引き落としの表示に使う。
- **振替**：同じ日・同じ金額の出金と入金の組が 1 組だけなら、自動で振替の組にする（[20.4節](#204-振替とチャージ)）。組は明細の「解除」で外せる（`DELETE /api/bank-transfers/link`）。
- 以前あった「毎月の入出金」の一覧・振替の登録（銀行 → 銀行）・振替紐付け・毎月の入出金の候補は、2026-10 に画面と API を削除した。

### 10.4 残高の推移

銀行管理のいちばん上に、借入金管理の「借入残高の推移」と同じ形で、総残高（今日の時点）と合計のグラフ、口座ごとの小さなグラフを出す。範囲は過去 12 か月（明細のある月から）から先の 12 か月まで。今月までは実線、先は破線。計算は `src/lib/ledger/cash-outlook.ts`、データは `GET /api/bank-accounts/cash-outlook`。

- 今月より前：明細から出した月末の残高（明細の合計 ＋ 差額）。
- 合計の今月：今日の残高 ＋（今月の予算の収支 − 今月これまでの実績の収支）。収支は収入 − 原価 − 費用（家計では貯蓄額）。今月の予算が無ければ今日の残高のまま。
- 合計の先の月：前の月の残高 ＋ その月の予算の収支。予算の無い月は、資金移動ルール（借入の返済の自動の引き落としも含む）の月の収支で代わりにする。
- 口座ごとの先の月：予算は口座ごとに分かれていないため、資金移動ルール（借入の返済も含む）の月の収支を積み上げる。

### 10.5 借入の返済の引き落とし

借入金管理で引き落とし口座と日を入れた借入の返済は、借入日の月から完済予定の月まで、月々の返済額をその口座からの引き落としとして、残高の推移の見込みに自動で並べる（`src/lib/assets/loan-funding.ts`）。同じ口座・日・金額（±1%）の資金移動ルールがあれば、そちらを使い借入からは入れない（二重に数えない）。

資金繰り（日ごとの残高と入金の期限）と資金フロー図（Sankey）は、画面から消したあと（2026-10）、API と計算も削除した。`GET /api/linked-accounts/flow` はカードごとの引き落としと固定決済（カード・電子マネー管理の一覧）だけを返す。

## 11. カード・電子マネー

### 11.1 登録できるもの

クレジットカード・デビットカード・プリペイドカード・電子マネー。名前・発行元・番号の下4桁・紐付く科目（資産か負債）を登録する。

### 11.1.1 サマリ

借入金管理と同じ並びで、次の 2 つを置く。

- **利用額の推移**: 今月の利用額の合計と合計のグラフ、カードごとの小さなグラフ。月の利用額は利用 − 返金で、チャージとチャージ先に入った側は除く。範囲は過去 12 か月（明細のある月から）から先の 6 か月まで。今月までは実線、先は固定決済の合計で見込んで破線（`src/lib/ledger/card-usage.ts`、`GET /api/linked-accounts/usage-trend`）。
- **カード・電子マネー**: 1 枚ずつ枠線つきの行で、種別・発行元・下 4 桁・今月の利用額・引き落とし（銀行口座・日・金額）・固定決済の件数と月額・紐付く科目を出す。右上の「カード・電子マネー追加」と、行の「明細を見る」（実績管理の履歴）・「編集」・「削除」。

### 11.2 明細と科目付け

- 明細を実績管理の CSV インポートで取り込み、実績管理の履歴（出どころはカード・電子マネー）で科目を付ける（付けた明細がそのまま実績になる。[10.2節](#102-明細)と同じ）。手で入れる利用・返金は、実績管理のカレンダーで登録する。
- 明細は銀行と同じく、入金をプラス、出金（利用）をマイナスで持つ（CSV も利用をマイナスで書く）。カレンダーで手で入れるときだけ、利用をプラス、返金をマイナスで入れ、保存のときに向きを変える。

### 11.3 チャージ

- カードから別のカード・電子マネーへのチャージは、チャージ先を選び、チャージ先の入金の明細と組にする。組にした明細はどちらも収支から除く。
- 組にする相手の候補は、日付と金額が近いものを順に出す。同じ日・同じ金額の相手が 1 つだけなら、取り込みのときと「まとめて自動処理」のときに自動で組にする（[20.4節](#204-振替とチャージ)）。
- 以前に登録した、摘要のキーワードでチャージにするルール（`card_transfer_rules`）は、CSV の取り込みで今も使う。ルールは履歴の画面で一覧と削除だけができ、新しくは登録できない。

### 11.4 カード払いの固定決済

- サブスクリプションなど、カードで決まった日に払うものを、明細の「その他」から登録する（摘要・日・金額・科目を引き継ぐ）。登録済みのものは書き換え・解除できる。
- サマリのカードの行に件数と月額を出し、利用額の推移の先の月の見込みに使う。
- 銀行の残高の見込みには含めない。お金はカード引き落としとして口座から出るので、含めると二重になる（[24章](#24-決定事項)）。

### 11.5 引き落としとの関係

カードの利用分を口座から引き落とす動きは、実績管理の履歴（出どころは銀行）で、引き落としの明細の「その他」→「毎月の入出金」からカード引き落としの資金移動ルールとして登録する。これが残高の推移の見込みに入る。

## 12. 資産と借入金

### 12.1 総資産サマリ

口座の残高 ＋ 実物資産の評価額 − 借入金の残高 で、純資産を出す。口座と実物資産で同じお金を二重に数えないようにしている（例：実物資産に「資産として数えない」を指定できる）。

ダッシュボードに置き、KPI の対象月の時点で出す。時点は月末（今月なら今日）で、それぞれ次のように出す。

- 実物資産：評価額の推移の見積もり（[12.2節](#122-実物資産)）の、その時点の値。取得日より前は 0。
- 口座：その時点までの明細の合計 ＋ 差額。
- 借入金（実物資産にひも付けた借入も同じ）：返済の記録があれば「借入額 − その時点までに返した元金」、無ければ返済予定から出したその時点の残高（`src/lib/assets/loan-balance.ts` の `loanBalanceAt`）。まだ借りていなければ 0。
- 資産・負債科目：その月以前でいちばん新しい月の残高。

### 12.2 実物資産

土地・建物・車・金・貴金属・現金（タンス預金）・預金・投資（株式・投資信託など）・その他。取得日・取得額・評価額を持ち、借入金を1件ひも付けられる（ひも付けた借入は、借入金管理のデータとして持つ）。

- **入力の場所**：資産管理では資産そのもの（名前・種別・取得日・取得価格・評価額・価値の変わり方・内訳）だけを入力する。借入の条件は借入金管理で入力し、ローンで買った資産は借入金管理の「借入追加」で一緒に作るか、資産管理で登録した資産を借入金管理でひも付ける（[12.3節](#123-借入金)）。資産管理には、ひも付いた借入の名前と残高を表示だけする。
- 資産を消しても、ひも付いた借入は消さない（借入金管理に残り、ひも付けだけ外れる）。

- **内訳**：住宅ローン 1 本で土地と建物を買ったときなどは、1 つの資産に内訳（`personal_asset_parts`）を持たせて 1 回で登録できる。資産とローンは 1 対 1 のまま、内訳ごとに種別・取得価格・評価額・価値の変わり方を持つ。内訳があるときの資産の評価額と取得価格は内訳の合計。
- **評価額の推移**：計算は `src/lib/shared/asset-valuation.ts`（モバイルと共有）。
  - 評価額の記録（`personal_asset_valuations`）は、登録時・評価額の更新時・価値の変わり方を変えたときに残す。
  - 記録には、その日から効く価値の変わり方（その時点の設定）も残す。記録した日から次の記録の前日までは、その値から記録の変わり方で見積もり、次の記録の日にその値へ切り替える。評価額を入れ直しても、過ぎた月の金額（ダッシュボードの総資産サマリを含む）は変わらない。
  - 価値の変わり方（自動のときは種別も）を変えたときは、変える前の設定での今日の見積もりを、新しい変わり方とともに記録する。変更は今日から先だけに効く。
  - 取得日の取得価格から最初の記録までは、ほかに情報が無いので直線で結ぶ。取得日・取得価格を直したときは、記録の誤りを直したものとして、この区間を描き直す。
- **価値の変わり方**：資産（内訳があれば内訳）ごとに選ぶ。

  | 変わり方 | 見積もり |
  |---|---|
  | 自動（既定） | 建物は構造の年数（木造 22・軽量鉄骨 27・重量鉄骨 34・鉄筋コンクリート 47 年）で取得価格から 0 円へ定額、車は毎年 20% の定率、土地・金・投資は年率（既定 0%）、現金・預金・その他は変わらない |
  | 変わらない | 最後に入れた評価額のまま |
  | 年率で増減 | 年率（%、マイナスで下落）の複利 |
  | 耐用年数で 0 円へ（定額） | 取得日から指定した年数で 0 円になるよう直線で減る |
  | 定率で減る | 毎年指定した割合で減る |

- 資産管理には、資産計上の資産の合計と、資産ごと（内訳があれば内訳ごとの線）の推移のグラフを出す。今月より先は破線。データは `GET /api/personal-assets/trend`。

### 12.3 借入金

- 借入先・金額・金利・借入日・返済日・種類（事業 / 住宅など）・月々の返済額・残価（最終回に残す額）を登録する。
- 月々の返済額は、元利均等で自動で計算する。手で入れた額を優先させることもできる。
- 資産管理と同じ形で、日付つきの借入残高合計と合計のグラフ、ローンごとの残高と金利の小さなグラフを出す（今月より先は破線の見込み・予測。残高と金利は別のグラフにし、軸を重ねない）。系列は `src/lib/shared/loan-schedule.ts` の `loanTrendSeries`（モバイルと共有）。返済を登録すると残高が減る。
- 予算に反映する科目を指定すると、月々の返済額が予算に自動反映される（[8.3節](#83-自動反映)）。実物資産にひも付いた借入も、この予算連携先に上乗せする。
- **この借入で買った資産**：「借入追加」で、資産をその場で作る（名前・種別・取得価格・評価額。取得価格の既定は借入額、取得日は借入日）か、ローンの無い既存の資産を選んでひも付ける。「借入条件の編集」で付け替え・外しができる。1 つの借入にひも付く資産は 1 つ。内訳や価値の変わり方は資産管理で直す。
- 金利が改定され、改定後の返済額が未入力の借入は、カードのいちばん上と画面の上にお知らせを出す。
- **引き落とし口座と日**：入れると、月々の返済額を残高の推移の見込みに自動で入れる（[10.4節](#104-残高の推移)）。同じ返済の資金移動ルールがあるときは、一覧にその旨を出し、ルールの方を使う。
- 「借入条件の編集」では、借入額・借入日・金利（金利変更の履歴が無いときだけ。あるときは「金利変更」で登録）・完済予定・月々の返済額・残価・予算連携先も直せる。借入額を直すと、残高も「借入額 − 返した元金の合計」に合わせる。
- **残高の計算**：返済の記録がある借入は「借入額 − その時点までに返した元金」、記録が無い借入は返済予定から計算したその時点の残高（`src/lib/assets/loan-balance.ts`）。借入金管理・ダッシュボードの総資産サマリ・資産管理の表示で同じ計算を使う。

### 12.4 金利の変更

変動金利の見直しを、適用日・新しい金利・（通知されていれば）実際の返済額で登録する。見直し前後の返済額と総返済額を比べて表示する。金利の履歴は追記だけで、消さない。

## 13. 会計帳簿

個人・法人モードで使う。

### 13.1 仕訳帳と承認

- 仕訳を、日付・摘要・支払方法・課税区分と、借方・貸方の明細（科目・金額・税率・仕入税額控除の対象か）で入力する。
- 仕訳には領収書などの証憑（画像・PDF）を添付できる。1 ファイルの上限は既定 10MB（環境変数 `UPLOAD_MAX_BYTES`）。
- 承認のワークフロー：仕訳は登録すると承認済みになる。必要なら承認申請 → 承認待ち → 承認済 / 差戻し の順に回す。申請・承認・差戻しはどれも accountant 以上が行う（電子帳簿保存法への対応）。
- 仕訳は、損益の科目について実績に自動で同期する。

### 13.2 仕訳テンプレートと仕訳の提案

- よく使う仕訳を雛形として登録・削除できる。仕訳帳から雛形を呼び出して入力する操作は、まだ無い。雛形の画面は科目の一覧を読み込めない不具合がある（[tasks/task.md](docs/tasks/task.md)）。
- 摘要から、借方・貸方の科目の組み合わせを提案する API がある（`POST /api/journals/suggest`。同じ摘要の過去の仕訳を使い、無ければキーワードの規則で決める。外部の AI は使わない）。画面からはまだ使っていない。

### 13.3 総勘定元帳・試算表

- 総勘定元帳：年・科目ごとの取引の一覧。CSV で出力できる。
- 試算表：決算処理の画面と API で出す。親子の科目をまとめて集計できる。部門での絞り込みは、決算書の API（`GET /api/closing/statements?departmentId=`）だけにある。

### 13.4 売掛金・買掛金・インボイス

- インボイス（適格請求書）を、下書き → 発行済み → 入金済み で管理する。発行すると売掛金を自動で作り、売掛金の入金を登録すると入金済みになる。インボイスの画面の「入金」と「印刷」のボタンは動かない不具合がある（[tasks/task.md](docs/tasks/task.md)）。
- 売掛金・買掛金は、未入金（未払）/ 入金済（支払済）/ 延滞 で管理する。入金・支払を登録すると、仕訳を自動で作る。

### 13.5 棚卸・固定資産・事業利用按分

- 棚卸：期末の在庫を品目・種類・数量・単価で入力し、評価方法（最終仕入原価法 / 総平均法 / 移動平均法）を記録して確定する（金額はどの方法でも数量×単価）。確定すると仕訳を記録する。
- 固定資産：取得日・取得額・耐用年数・償却方法（定額法 / 定率法）で登録し、年度ごとに減価償却を計算する。償却すると仕訳を記録する。
- 事業利用按分（個人のみ。家事按分）：経費の科目ごとに、事業で使う割合を設定する。明細を事業利用にしたときの按分の初期値になり、決算と事業利用按分計算書は明細ごとの按分で計算する（[20.15節](#2015-事業利用と按分)）。

## 14. 決算と申告

### 14.1 決算処理

年度を選び、次のタブで確かめる。

| タブ | 内容 |
|---|---|
| 損益計算書 | 収益・費用・利益 |
| 貸借対照表 | 資産・負債・純資産 |
| 月別収支 | 月ごとの収支 |
| 試算表 | 科目ごとの借方・貸方 |
| 財務分析 | 流動比率・自己資本比率・ROA・ROE など |

### 14.2 決算確定

決算を確定すると、その会計年度を締める（純利益を記録する）。取り消して開き直せる。確定と取り消しは editor 以上。会計年度管理に無い年は、暦年の会計年度を自動で作る。

### 14.3 申告書類の印刷

| 画面 | 内容 |
|---|---|
| 青色申告決算書・収支内訳書（個人） | 損益計算書、月別収支表、貸借対照表（青色のみ）、事業利用按分計算書（事業の割合が 100% 未満の科目があるとき）。事業者情報の青色申告の設定で、どちらを出すかが決まる |
| 法人決算書類（法人） | 損益計算書、貸借対照表、株主資本等変動計算書、財務指標、法人税・地方税の概算 |

### 14.4 e-Tax XML

青色申告決算書・法人税申告書・消費税申告書を、e-Tax / eLTAX 向けの XML として出力する（accountant 以上）。

### 14.5 消費税

年度ごとに課税方式（免税 / 原則課税 / 簡易課税。簡易課税ならみなし仕入率）を設定する。年度の設定がないときだけ、事業者情報の既定値を使う。仕入税額控除の対象を集計する API がある（`GET /api/tax-credit`。画面からはまだ使っていない）。

## 15. 法人管理

### 15.1 法人・事業者情報

テナントの種別・名前・法人番号・資本金・設立日・会計期間（開始月・決算月。開始月は決算月の翌月）。会計期間は設定の基本設定でも変えられる。個人事業主の屋号・事業主名・開業日・青色申告・インボイス登録番号は、設定の基本設定で管理する。

### 15.2 会計年度

会計年度の開始日・終了日を登録し、開いている / 締めた を切り替える。

### 15.3 ガバナンス

| タブ | 内容 |
|---|---|
| 役員管理 | 氏名・役職・任期・報酬 |
| 株主総会 | 開催日・種類（定時 / 臨時）・議題・決議（議事録の URL の列はあるが、画面には欄が無い） |
| 配当管理 | 決議日・支払日・1株あたりの額・総額 |

- 共有するファイルは `app/web/src/lib/shared/shared-with-mobile.ts` の一覧で管理する（今は 17 ファイル。予算配分の振り分け・金額の向きの言葉・資産の評価・予算と実績のグラフ・予算のセルの内訳・予算の月の流れ・対象月・借入の償還・表示名・科目×月の表・ヘルプ文・ラベル・モード別の用語・変動金利の予測・ステップ進捗など）。

**開発環境（`platform/docker-compose.yml`）**

| サービス | イメージ・起動方法 | 役割 |
|---|---|---|
| `web` | `platform/docker/web.Dockerfile` でビルド。ポート 3000。証憑はボリューム `uploads_data` | 画面と API。起動時に entrypoint がマイグレーションを適用し、DB が空なら初期データを入れる。`NODE_ENV=production`・`COOKIE_SECURE=false` で動くので、Cookie の名前は `fm_session` |

**web のイメージと起動処理**

- `web.Dockerfile`（Node.js 22）は、依存関係の取得 → `prisma generate` と `next build` → 実行用、の段階でビルドする（ビルドにはダミーの `DATABASE_URL` を渡す）。lint と型の検査は CI で行うので、イメージのビルドでは飛ばす（`--no-lint`・`SKIP_TYPECHECK=1`）。

## 19. 認証の実装

| クライアント | 方式 | 保存場所 |
|---|---|---|
| Web | セッション Cookie（httpOnly・`SameSite=Lax`。`NODE_ENV=production` で `COOKIE_SECURE` が `false` でなければ `__Host-fm_session`（Secure つき）、それ以外は `fm_session`） | ブラウザ |
| モバイル | `Authorization: Bearer <トークン>`（ログインの応答の `data.sessionId`） | expo-secure-store |

- **パスワード**：`scrypt`（N=32768, r=8, p=1）で保存する。古い形式（N=16384）のハッシュは、次にログインに成功したときに作り直す。存在しないメールアドレスでも同じ計算をして、応答時間の差でアカウントの有無が分からないようにする。
- **セッション**：`fm2:` ＋ 32バイトの乱数をトークンとし、DB には SHA-256 のハッシュだけを保存する。ログインのたびに新しいトークンを発行する。admin がユーザーのパスワードかロールを変えると、そのユーザーのセッションをすべて消す。
- **多要素認証**：ログインで `401 {mfaRequired, mfaToken}` を返し、`/api/auth/mfa/verify` で確認コード（またはリカバリーコード）を受け取る。チャレンジはハッシュで保存し、5分・5回まで有効で、超えるとアカウントを15分ロックする。同じ確認コードの再利用を防ぐ。
- **CSRF**：`/api/*` の変更系のリクエストを、次の順に確かめる（`src/lib/server/csrf.ts`）。
  1. Bearer トークンか `X-Requested-With: fm-mobile` を付けたリクエスト（モバイル）は対象外。
  2. `Sec-Fetch-Site` があれば、`same-origin` か `none` であること。
  3. 無ければ、`Origin` が `APP_ORIGIN`（未設定ならリクエスト自身のオリジン）と一致すること。
  4. どちらのヘッダーも無いリクエストは、セッション Cookie を持っていなければ通し、持っていれば断る。
- **レート制限**：Redis の固定時間枠で数える。ログインは IP ごとに5分で10回（Redis が使えないときはメモリで数える）。CSV の取り込みと同期は、ユーザーごとに10分で10回。
- **ページの保護**：`middleware.ts` が、Cookie のない画面へのアクセスを `/login` に転送する。セッションの有効性は API 側で確かめ、API が 401 を返すと、画面はログインへ戻す。

## 20. 機能ごとの実装方針

### 20.1 テナント分離

`src/lib/server/tenant-db.ts` の `tenantDb(tenantId)` は、Prisma の `$extends` で、`tenantId` を持つすべてのモデルの検索条件と作成データに `tenantId` を差し込む。対象のモデルは起動時に `Prisma.dmmf` から集める（`User` と `LearningProgress` は除く）。ID を指定した操作で他のテナントのデータを指したときは 404 を返す。

### 20.2 API の共通処理

ほぼすべての API は `src/lib/server/api-handler.ts` の `withApi({ role, schema, querySchema, handler })` で書く。`withApi` は次を順に行う。

1. `requireRole` でログインとロールを確かめる（401 / 403）。
2. パスの `[id]` が正の整数であることを確かめる。
3. 本文とクエリを Zod で検査する。
4. テナントで絞った `db` と、監査ログを書く `audit()` をハンドラーに渡す。
5. 例外を `src/lib/server/api-error.ts` で決まった形のエラー応答にする。

`withApi` を使わないのは、ログイン・ログアウト・多要素認証の確認・`GET /api/auth/me`・ヘルスチェック・定期ジョブ用の `/api/admin/cleanup`・Stripe の通知を受ける `/api/webhooks/stripe` の 7 つ（`PATCH /api/auth/me` は `withApi` を使う）。

### 20.3 口座の残高

残高の定義は `src/lib/ledger/bank-balance.ts` の1か所だけに置く：`SUM(financial_records.flow)`（その口座の銀行明細）`+ bank_accounts.balanceAdjustment`。口座一覧・口座残高サマリ・総資産サマリはこれを使う。残高の推移（`src/lib/ledger/cash-outlook.ts`）も同じ定義（明細の合計 ＋ 差額）を、月ごとに積み上げて出す。

### 20.4 振替とチャージ

- **自動相殺**：明細の登録・CSV の取り込み・自動取得のあと（その日付の明細）と、「まとめて自動処理」（全期間）で、同じ日・同じ金額の出金と入金の組が 1 組だけ（出金側にも入金側にもほかの候補が無い）なら、振替・チャージの組にする（`src/lib/ledger/auto-offset.ts`）。銀行 → 銀行は振替、銀行・カード → デビット・プリペイド・電子マネーはチャージ。確定済みの月の明細は対象にしない。
- **振替**：2つの口座の明細に同じ `transferGroupId` を付ける。組は自動相殺だけで作り、明細の「解除」で外せる。
- **チャージ**：チャージ元の明細（銀行・カードとも `financial_records.chargeToCardId`）と、チャージ先の入金の明細に、同じ `chargeGroupId` を付ける。`chargeGroupId` は銀行とカードの明細で共通の番号を使う。候補の順位付けと組の検査は `charge-link.ts`。
- `transferGroupId`・チャージ先・`chargeGroupId` のいずれかを持つ明細は、科目を持たない（実績に入らない）。組にするときは付いていた科目を外す（CHECK 制約 `financial_records_pair_no_account_check`）。

### 20.5 カード払いの固定決済

カード払いの固定決済は `card_recurring_payments` に置き、資金移動ルール（`transfers`）には入れない。`transfers` は銀行の残高の見込みに使うので、ここに入れるとカード引き落としと二重に数えてしまう。

### 20.6 明細と実績、仕訳の同期

- 明細は実績の表の 1 行なので、転記（写しの行を作ること）は無い。科目を変えると、その行の `accountId` と `amount`（`signedActualAmountFromSpend(区分, −flow)`。`src/lib/ledger/ledger-entries.ts` の `entryActualAmount`）を一緒に直す（`src/lib/ledger/ledger-categorize.ts`）。
- 実績を読む所は、科目のある行だけに絞る（`src/lib/ledger/actuals.ts` の `ACTUAL_WHERE` と `actualRows`）。
- 仕訳から実績への同期は `src/lib/accounting/journal.ts` の `syncJournalToFinancialRecords` の1か所で行う。作った実績には `journalEntryId` を記録し、仕訳を消すときに一緒に消す。
- 同期するのは損益の科目だけで、資産・負債の科目は対象外（残高のスナップショットとして別に扱う）。
- 符号は、仕訳の借方・貸方が科目の自然に増える側と同じならプラス、逆ならマイナスとする。
- 売掛金・買掛金の発生と消込、棚卸の確定、減価償却は、監査のための仕訳も記録する。

### 20.7 予測

`src/lib/budget/forecast.ts` に、線形回帰・移動平均・成長率・Holt・Holt-Winters と、過去のデータでの検証（MAPE・RMSE）を実装している。既定の手法は、KPI と推移（`/api/reports/monthly-trend`）が移動平均、予測の API（`/api/forecasts`）が線形回帰。変動金利の先の見込みは `src/lib/shared/rate-forecast.ts`。

### 20.8 キャッシュ

`src/lib/server/redis.ts` の `withCache(key, ttl, fn)` で、重い集計を1時間キャッシュする。Redis につながらないときは、キャッシュなしで計算する。

| キー | 内容 | 消すタイミング |
|---|---|---|
| `assets:summary:{tenantId}:{年月}` | 総資産サマリ | 口座・銀行の明細・取り込み・まとめて自動処理・振替とチャージの組・借入金（登録・変更・返済・金利）・実物資産の変更（と期限切れ） |
| `closing:statements:{tenantId}:{年}[:dept:{部門}]` | 決算書 | 決算確定、仕訳の登録・削除（と期限切れ） |
| `reports:ledger:{tenantId}:{年}:{科目 ID か all}` | 総勘定元帳（JSON のときだけ。CSV はキャッシュしない） | 決算確定、仕訳の登録・削除（と期限切れ） |

決算書と総勘定元帳のキーは `src/lib/server/closing-cache.ts` の `invalidateClosingCaches(tenantId, 年)` でまとめて消す。決算確定の取り消しと、自動で作る仕訳（減価償却・棚卸の確定・売掛金と買掛金の消込）では、今は消していない（[tasks/task.md](docs/tasks/task.md)）。

### 20.9 勘定科目変換の判定

`src/lib/accounting/account-conversion.ts` で、家計の科目ごとに次の順で変換先を決める。

| 順 | 判定 | 信頼度 |
|---|---|---|
| 1 | 変換ルールの表（自分のルールを優先し、次にシステム定義） | ルールの値（既定 1.0） |
| 2 | キーワードの一致（科目名に「税」「保険」などを含む） | 0.9 |
| 3 | あいまいな一致（科目名の bigram の Dice 係数。0.5 以上） | 類似度 |
| 4 | 区分ごとの既定（収入 → 売上高、変動費 → 仕入高、固定費 → 雑費） | 0.4 |
| 5 | 候補なし | — |

信頼度 0.8 以上を「自動」、0.5〜0.79 を「要確認」、それ未満を「手動」とする。変換のルール・履歴はテナントではなくユーザーに属する。有料の AI 変換のテーブル（`ai_conversion_results`・`ai_conversion_usages`）はスキーマだけあり、使っていない。

### 20.10 証憑のアップロード

証憑は仕訳と現金の明細に付けられる。ファイルの先頭のバイトで種類を確かめてから保存する（`src/lib/server/upload.ts` の `readUploadedFile`・`storeTenantUpload`）。証憑や明細を消すと、ファイルも消す。

置き場所は `UPLOAD_STORAGE` で選ぶ（`src/lib/server/storage/`）。

- `local`（既定）: web コンテナの `/app/uploads`（ボリューム）に、テナントごとのフォルダで置く。旧構成の平置きのファイルも読める。
- `r2`: Cloudflare R2 のバケットに、キー `<tenantId>/<保存名>` で置く。バケットは非公開にし、配信はアプリを通す。R2 に無いファイルはローカルから読むので、既存のファイルを移す前でも配信は切れない。移し方は [runbooks/uploads-to-r2.md](docs/runbooks/uploads-to-r2.md)（`scripts/migrate-uploads-to-r2.ts`）。

`/api/uploads/[filename]` から、ログインしたユーザーに、自分のテナントの証憑だけを返す（ほかは 404）。ダウンロードは監査ログに残す。

### 20.11 定期ジョブ

| ジョブ | 方法 | 内容 |
|---|---|---|
| 期限切れのセッションの削除 | `session-cleanup` コンテナの crond（毎日 2:00。時刻はコンテナの時刻で、alpine の既定は UTC） | `POST /api/admin/cleanup` を `Authorization: Bearer <CLEANUP_SERVICE_KEY>` で呼び、期限切れのセッションと多要素認証のチャレンジを消す |

### 20.12 バックアップ

`platform/scripts/backup.sh` が `pg_dump` を gzip で保存し、`RETENTION_DAYS`（既定30日）より古いものを消す。戻すのは `restore.sh`。手順は [runbooks/backup-restore.md](docs/runbooks/backup-restore.md)。

### 20.13 有料プラン

有料プランは Stripe で申し込む。契約はテナントに 1 行（`subscriptions`）で、行が無いテナントは無料プラン。申し込みと支払いの管理は admin が設定の「プランと支払い」から行い、プランはそのテナントの全ユーザーで共通。

- 有料プランかどうかは `src/lib/billing/plan.ts` の `isPremiumSubscription` だけで決める。ACTIVE・TRIALING は有料。PAST_DUE（支払いの失敗）は、失敗してから 7 日のあいだだけ有料のまま。
- 申し込みは Stripe Checkout、支払い方法の変更・解約は Stripe Customer Portal の画面で行う（`src/lib/billing/checkout.ts`）。カード番号はこのアプリに保存しない。
- 契約の状態は Stripe の通知（`POST /api/webhooks/stripe`）で更新する（`src/lib/billing/webhook.ts`）。通知は署名で確かめ、処理した通知の ID を `stripe_webhook_events` に残して二度処理しない。受け取るのは `checkout.session.completed`・`customer.subscription.created/updated/deleted`・`invoice.payment_failed`。
- `STRIPE_SECRET_KEY` と `STRIPE_PRICE_ID` が無ければ、申し込みは 503（準備中）。通知を受けるには `STRIPE_WEBHOOK_SECRET` も要る（`platform/.env.example`）。
- 有料プランが要る機能は 402 と `code`（例 `premium_required`）を返す（`src/lib/server/api-error.ts` の `paymentRequired`）。
- 契約が残っているテナントは削除できない（409）。先に解約する。

### 20.14 レシートの読み取り

実績管理の現金のカレンダーで「レシートを撮影して入力」を押すと、撮った写真から日付・店名・合計・支払方法を読み、登録のフォームに入れる。読み取りでは何も登録せず、利用者が確かめてから登録する（`src/lib/ledger/receipt-scan/`）。

- 写真はブラウザで長辺 1600px の JPEG に縮めてから送る（`src/lib/client/resize-image.ts`）。読み取りでは画像を残さず、登録したあとに、その明細の証憑として付ける（`POST /api/actuals/[id]/receipts`）。カレンダーの明細の行に 📎 が付き、証憑を開ける。
- 有料プランは Claude（`RECEIPT_OCR_MODEL`、既定 `claude-opus-5-5`）の構造化出力で読む。無料プラン、または `ANTHROPIC_API_KEY` が無いときは、サーバーの中の Tesseract（日本語の学習データは `@tesseract.js-data/jpn` を同梱）で読み、`parse-receipt-text.ts` で「合計」などの手がかりから拾う。Tesseract は同時に 1 件だけ動かす。
- 回数はテナントごとに日本時間の 1 日 30 回まで（`receipt_scan_requests` を数える。失敗は数えない）。上限を超えると 429。テナントの行をロックしてから数えるので、同時に読んでも超えない。
- 店名は学習ルールにかけ、当たれば科目の候補にする。登録のときに「次から同じ店名には、この科目を使う」を選ぶと、学習ルールに覚える（`POST /api/actuals` の `learn`）。
- カード払い・電子マネーと読めたときは、明細から入る分と二重に計上しないよう注意を出す。
- モバイルアプリでも同じ API で読み取る（`expo-image-picker` で撮影・選択し、`expo-image-manipulator` で縮める）。読み取りは通常の API より時間がかかるので、打ち切りまでの時間を延ばしている（`app/mobile/src/api.ts`）。

### 20.15 事業利用と按分

明細（現金・銀行・カード）ごとに、事業で使ったか（`financial_records.businessUse`）と、事業の分の割合（按分 `businessRatio`、0 より大きく 100 以下の %）を持つ。個人事業主モードで、事業の分として数えるために使う。

- 事業の分の額は保存せず、読むときに `src/lib/shared/business-use.ts` の `businessPortion`（金額 × 按分 ÷ 100、明細ごとに円未満を 0 に向けて切り捨て）で計算する。
- 事業利用にして按分を省略すると、科目の事業利用按分（`apportionments.businessRate`）の割合、無ければ 100% にする（`src/lib/ledger/business-use.ts`）。
- 振替・チャージの組と、明細でない行は事業利用を持たない。事業利用なら按分が必須。どちらも CHECK 制約で守る。組にした明細は事業利用を外す。
- 学習ルールも事業利用を持つ（[9.4節](#94-学習ルール)）。
- 口座・カード・電子マネー・実物資産・借入金も事業利用（`businessUse`）を持つ。事業利用の口座・カードに入る明細（CSV の取り込み・自動取得・手入力）は、学習ルールが決めていなければ事業利用で入る。CSV インポートの `?business=1` でも事業利用で取り込める。

**個人事業主モードの画面**：画面は表示モードから範囲を決めて送る（`src/lib/client/use-view-mode.ts` の `useActualsScope`。モードを読むまでは取得しない）。

- 実績管理の明細の一覧（現金・銀行・カード）は、個人事業主モードでは「事業利用のみ」に絞り（切り替えで全件）、事業利用の明細に「事業 n%」を付ける。現金のカレンダーは事業の分の額で出し、登録は事業利用で始める（按分を空けると科目の事業利用按分の割合）。CSV インポートには「事業利用として取り込む」を出す。
- 口座・カード・実物資産・借入金の登録と編集に「事業利用」を出す。個人事業主モードで足すときは事業利用で始める。
- 画面の作りと科目名は家庭モードにそろえる（`displayName` は個人事業主モードでも家庭科目名を返し、説明文も家庭モードのものを使う。KPI の見出しは事業の用語のまま）。
- メニューは、家庭モードの画面に、個人事業主・青色申告に要る画面（仕訳帳・総勘定元帳・売掛金・買掛金・インボイス・棚卸・固定資産・事業利用按分・決算処理・会計年度・税理士ポータル）を足したもの。仕訳テンプレート・外部サービス連携・勘定科目変換・学習ガイドは法人モードだけに出し、メニューに無い画面を URL で開いたときはダッシュボードへ戻す。

**実績の範囲（scope）**：実績や口座を返す API は `?scope=household|business` を受け付ける（既定は household。`src/lib/ledger/scope.ts`）。

- household（家庭・法人モード）は全件・全額。
- business（個人事業主モード）は、事業利用の明細を按分した額と、明細でない行（仕訳・減価償却・棚卸など）の全額だけを数え、口座・カード・実物資産・借入金は事業利用のものだけを出す。
- 対象は KPI・科目×月・推移・予測・税理士ポータル・決算書・e-Tax と、口座・カード・資産・借入金の一覧とサマリ・資金繰り。
- 決算書の費用は、明細の全額（total）と事業の分（deductible）を分けて出し、按分率（businessRate）はその比。household では按分しない。キャッシュのキーに範囲を入れ、明細の登録・削除・科目や事業利用の変更・取り込みで消す。

**個人事業の予算**：予算は家庭と個人事業で別々に持つ（`BudgetScope`。予算・カレンダーの内訳・変更履歴・予算の確定・配分ルール・科目の振り分けの各テーブルの `scope`。`src/lib/budget/budget-scope.ts`）。予算の API は同じ `?scope=business` で事業の予算を扱う。

- 個人事業主モードの予算管理（一覧・カレンダー・予実差確認・予算の確定・履歴・設定）と、ダッシュボードの予算と実績のグラフ・確定の状況は、事業の予算を扱う。実績管理の実績の確定タブに出す予算の確定の状況も、いまのモードの予算のもの。
- 予算の一覧・カレンダー・予実差・予算の確定・履歴・配分提案は、家庭と同じ流れで使う。予実差は事業の予算と事業の分の実績を比べ、借入の返済と実物資産の負債の上乗せは事業利用のものだけを入れる。
- 予算の確定は範囲ごと（`budget_confirmations` は `[periodId, scope]` で一意）。実績の確定は共通で、その月の予算がどちらかで確定していればよい。実績の確定を解除できないのは、翌月の予算がどちらかで確定しているとき。
- 配分ルールは事業用の既定を別に持つ（[8.2節](#82-予算配分)）。新しいテナントには家庭と事業の両方の既定を入れる。
- KPI・推移・資金繰りの予算も範囲ごと。家庭の資金繰りの見込みは家庭の予算だけを使う（事業の予算を二重に数えない）。
- 画面：個人事業主モードでは、予算管理の各タブ（一覧・カレンダー・予実差確認・予算の確定・履歴・設定）と、ダッシュボードの予算と実績のグラフ・確定の状況が事業の予算を扱う。実績の確定タブに出す予算の確定状況も、いまのモードの予算のもの。配分ルールのグループは「生活費」の代わりに「変動費」、余りの回し先の既定は「事業主の取り分」に入る科目。

### 20.16 実績から作る仕訳

個人事業主モードの仕訳帳・総勘定元帳・試算表は、仕訳を手で入れず、実績から複式の仕訳を作って見せる（青色申告の 65 万円控除の、複式簿記の帳簿のため）。保存はせず、表示のたびに作るので、実績を直せば帳簿もそのまま変わる。作り方は `src/lib/accounting/auto-journal.ts`（純関数）、データの読み込みは `auto-journal-data.ts`。年度は暦年。

- **事業利用の明細**：科目に事業の分（按分した額）を立てる。出どころが事業用の口座・電子マネー等なら明細の全額をその口座に立て、家計の分は事業主貸（出金）・事業主借（入金）になる。例：事業用の口座から通信費 3,000 円を 50% で払った → 借方 通信費 1,500・事業主貸 1,500／貸方 普通預金 3,000。
- **現金とクレジットカード**：帳簿に残高を持たない。事業利用の支払いは、事業主が立て替えたものとして相手を事業主借にする（現金は残高を記録していないのでマイナスになるのを避けるため。カードは、引き落としの明細がどのカードの分かを明細から決められないため）。
- **事業用の口座・電子マネー等の、事業利用でない明細**：口座と事業主貸（出金）・事業主借（入金）。振替・チャージの組は、両方が事業用なら口座どうしの振替、片方だけなら事業主貸・事業主借。
- **明細でない実績の行**：仕訳から入った行は、その仕訳をそのまま使う。仕訳の無い行（直接入力）は相手を事業主借・事業主貸にする。減価償却のように、同じ科目・同じ額の仕訳が別にあるときはその仕訳を使う。
- **実績に入らない仕訳**：損益の科目を含まないもの（売掛金・買掛金の消込など）はそのまま含める。損益の科目を含むもの（棚卸の確定など）は決算書と合わなくなるので含めず、仕訳帳に件数と一覧を出す。
- **期首**：事業用の口座・電子マネー等の、年度の初めの残高（前年までの明細の合計 + 差額）を元入金として立てる。
- **科目**：普通預金・預け金は口座・カードごとの補助科目に分ける。事業主貸・事業主借・元入金・普通預金・預け金は、同じ名前の科目が 1 つだけあればその科目を使い、無ければ帳簿の中だけの科目として出す（勘定科目の一覧には足さない）。
- 損益の科目は、決算書（`scope=business`）と同じ実績の行・同じ事業の分の額から作るので、試算表の所得（収入 − 原価 − 経費）は決算書の所得と一致する。借方と貸方の合計も一致する。
- API：`GET /api/journals/auto?year=&month=`（仕訳帳）、`GET /api/reports/general-ledger?scope=business`・`GET /api/reports/trial-balance?scope=business`（総勘定元帳・試算表。CSV も出せる）。
- 画面は閲覧と印刷だけ（入力・承認・証憑の操作は出さない）。印刷はブラウザの印刷で、メニューと操作のボタンは印刷しない。
- 固定資産の取得や期首の帳簿価額は、まだ帳簿に入れていない（減価償却の仕訳だけが入る）。

| 項目 | 内容 |
|---|---|
| 認証 | パスワード（scrypt）＋ 多要素認証（TOTP）、アカウントのロック、レート制限（[19章](#19-認証の実装)） |
| 認可 | 4段階のロールと、テナントによるデータ分離（[20.1節](#201-テナント分離)） |
| セッション | ハッシュで保存、アイドル24時間・最長7日（環境変数 `SESSION_IDLE_HOURS`・`SESSION_ABSOLUTE_DAYS` で変えられる）、ログインのたびに作り直す |
| CSRF | Origin・Sec-Fetch-Site の確認（Bearer とモバイルの識別ヘッダーは対象外。どちらのヘッダーも無くセッション Cookie を持つリクエストは断る。[19章](#19-認証の実装)） |
| 通信 | 本番は TLS。本番の Cookie は `__Host-` 付き・Secure |
| 監査 | 主な操作を監査ログに残す（帳簿と法人の操作は対象外。秘密の値は伏せる。[6.4節](#64-監査ログ)） |
| アップロード | 1 ファイル 10MB まで（`UPLOAD_MAX_BYTES`）。PDF と画像（jpg・png・gif・webp）だけで、ファイルの先頭のバイトでも種類を確かめる。R2 に置くときもバケットは非公開で、配信はテナントを確かめるアプリの API だけ。R2 の API トークンはそのバケットの読み書きだけに絞る |
| 設定 | 主な環境変数（DB・Redis・掃除の鍵・Cookie・セッション・アップロードの上限・APP_ORIGIN）を、最初に使うときに Zod で検査する（`src/lib/server/config.ts` の `getConfig()`。スキーマは `config-schema.ts`）。外部連携の変数は検査しない |

# 付録

## 24. 決定事項

| 番号 | 決めたこと | 理由 |
|---|---|---|
| D-1 | 銀行口座の台帳を `bank_accounts` に一本化し、`linked_accounts` はカード・電子マネー専用にする | 同じ口座が2つの台帳に分かれ、残高と明細が食い違っていたため |
| D-2 | 会計年度の開閉を `fiscal_years` に一本化する（`fiscal_year_closes` を統合） | 締めの状態の二重管理をなくすため |
| D-3 | インボイスを発行したら売掛金を自動で作り、`receivables.invoiceId` で結ぶ | 請求と売掛の入れ直しをなくすため |
| D-4 | 実物資産の負債を `loans` に移し、`personal_assets.loanId` で参照する | 借入の表し方を1つにして、返済スケジュールと予算への反映を共通にするため |
| D-5a | 仕訳から作った実績に `journalEntryId` を記録する | 仕訳を消したときに、実績も一緒に消すため |
| D-5b | 仕訳の同期は損益の科目だけにし、符号は科目の自然な増加側で決める | 資産・負債は残高のスナップショットとして扱っているため |
| D-5c | 実績への同期は `syncJournalToFinancialRecords` の1か所を通す | 経路ごとに同期がずれないようにするため |
| D-5d | 売掛・買掛の発生と消込、棚卸の確定、減価償却では、監査のための仕訳も記録する。発生時点で売上・仕入を実績に計上すること（発生主義）はしない | 試算表・総勘定元帳に記録を残しつつ、実績の意味を変えないため |
| D-6 | 課税方式は年度ごとの `tax_settings` を正とし、ないときだけ事業者情報の既定値を使う | 年度によって課税方式が変わるため |
| — | カード払いの固定決済は `transfers` に入れず `card_recurring_payments` に分ける | 銀行の残高の見込みで、カード引き落としと二重に数えないため（[20.5節](#205-カード払いの固定決済)） |
| — | 口座の残高は「明細の合計 ＋ 差額（`balanceAdjustment`）」に一本化する | 明細の取り込み前の残高を扱えるようにし、残高の定義を1か所にするため（[20.3節](#203-口座の残高)） |
| — | 振替とチャージの明細は、科目を付けず実績から除く | お金の置き場所が変わるだけで、収支ではないため |
| — | 勘定科目変換は対応の提案と記録までとし、既存データの科目の付け替えはしない | データの整合性と巻き戻しの設計が決まっていないため |
| — | 予実対比レポート（`/reports`）は廃止する | 画面の役割を整理したため |
| — | 科目別の予実対比は「予算の確定」で行い、確定した月の予算は変えられなくする。余りは原則として繰り越さず、期ズレと回し先へは科目ごとに選ぶ | 会社の予算管理にならい、比べる基準を動かさず、予算を使い切る動機を生まないため |
| — | KPI は利益率・前月比・前年同月比をやめ、決算月で締める期の年間見込み（未入力の月は入力済み月の平均で按分）を出す | 1 か月分の入力でも 1 年分（年収・年間の貯蓄）の目安がわかるようにするため。年間の集計は決算の単位にそろえるため |
| — | 予算確定 → 実績確定 → 翌月の予算確定の順を API で強制し、実績を確定した月の実績は変えられなくする。実績の「入力済み」は明細の最終日から自動で判定するが、確定はユーザーが押す | 比べる実績を固定してから翌月の予算を決めるため。明細の取り込み漏れや未割り当てをユーザーが確かめてから確定できるようにするため |
| — | 予実差確認と予算の確定（予算案を含む）は予算管理、実績の確定は実績管理のタブに置き、ダッシュボードには確定の状況・予算と実績のグラフ・総資産サマリを置く | 操作はそれぞれのデータを扱う画面にまとめ、毎回開くダッシュボードでは状況と差をひと目で確かめられるようにするため |
| — | 総資産サマリはダッシュボードの KPI の対象月の時点で出す | 画面の数字がすべて同じ月を指すようにするため |
| — | 土地と建物のように 1 本のローンで買った資産は、資産を分けずに内訳を持たせる | ローンと資産の 1 対 1 を保ったまま、価値の変わり方（土地は横ばい、建物は減る）を分けて見積もるため |
| — | 明細が月末まで届かないソースは「当月末まで変動なし」の申告で確定できるようにし、申告と確定時点の最終日を記録する | 引き落としの少ないカードなどで確定が止まらないようにしつつ、何を根拠に確定したかを後から確かめられるようにするため |
| — | 予算配分のルールと科目は保存した結び付けではなく、キーワードと区分でその場で振り分ける。手で移した分だけ保存する。予算への反映は予算未設定の科目だけに入れる | 追加した科目も自動で配分に入れ、1 ルールに複数の科目をまとめられるようにするため。入力済みの予算を配分で上書きしないため |
| — | 実績の直接の入力と取り込み（Excel・科目×月の CSV）は廃止し、実績は明細（現金・銀行・カード）に科目を付けて作る。CSV の取り込みは明細だけ（`POST /api/imports`） | 実績と明細を 1 つの表で扱い、出どころをたどれるようにするため。依存するライブラリの管理の負担を減らすため |
| — | 銀行・カードの明細を実績の表（`financial_records`）にまとめ、明細と口座・組と科目の決まりを CHECK 制約で守る | 写しの行をなくし、明細と実績が食い違わないようにするため |
| — | テナントに期の開始月（`startMonth`）を持たせ、決算月の翌月であることを CHECK 制約で守る。予算の確定には開始月の例外を設けない（はじめての予算は配分提案で入れる） | 期の区切りを明示するため。開始月の例外は、はじめての予算を入れる手段（配分提案）を予算の確定に置いたので外した |
| — | 予算管理のカレンダーで登録した予算は `budget_items` に 1 件ずつ持ち、`budgets.amount` に足す | 科目×月の予算の形を変えずに、日付つきの予算の内訳を残すため |
| — | 言語の切り替え（日本語 / English）はなくし、画面は日本語だけにする | 切り替えてもログアウトの表記しか変わらず、英語の画面が実質なかったため |
| — | 個人事業主モードの仕訳帳・総勘定元帳・試算表は、実績から表示のたびに作る（保存しない） | 仕訳を手で入れずに複式簿記の帳簿をそろえるため。保存すると、実績を直すたびに仕訳を作り直す必要があるため |
| — | 個人事業の予算は家庭と別に持ち（予算の各テーブルに scope）、予算の確定も別々にする。実績の確定は共通 | 事業と家計で予算の立て方（売上に対する割合と手取りに対する割合）が違い、混ぜると予実差が読めないため。実績は同じ明細を按分して両方に数えるので、確定は 1 回で済む |
